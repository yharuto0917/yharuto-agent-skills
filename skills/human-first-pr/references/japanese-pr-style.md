## 1. Chat PR 解説における日本語 8 原則（`/yomiyasu` 準拠）

### 1.1 文体原則：敬体（「です・ます」調）既定と混在禁止

- **敬体（「です・ます」調）を既定とする**: エージェントが Chat 上でユーザー（レビュアー・開発者）に向けて PR の内容を解説する場面では、自然で読みやすい **敬体（「です・ます」調）** を基本とする。
- **常体指定時の統一と混在禁止**: ユーザーの指示や `CLAUDE.md` / `AGENTS.md` で常体（「だ・である」調）が求められている場合のみ常体で統一し、**1 つの解説内で敬体と常体を混ぜない**。
- **地の文の述語明記と体言止めの線引き**: 地の文で「〜して、処理速度を改善。」のような **`て` 形の体言止め** は使わず、必ず述語まで言い切る。一方、変更ポイントの箇条書きや「読むべきファイル」表のセル内では、1 項目 1 要素の簡潔な体言止めを併用してよい。

### 1.2 事実根拠の厳格化と「既存 PR 説明文」の切り分け（`BR006` 対応）

- **断定できる一次根拠は 3 つだけ**: 事実として言い切ってよい根拠は **① 実際の Diff とリポジトリ内のコード、② エージェント自身が読み取り専用で実行確認したコマンド出力、③ ユーザーが提示した背景情報・Issue** に限る。一般知識や推測で原因・性能向上率・運用予定を補わない。
- **既存 PR 説明文との明確な区別**: PR 作成者が書いた既存の PR 本文やチェックリストは「未検証の参考情報」として扱う。PR 作成者になりすまして `- [x] 全テストを実行しパスを確認済み` と書いたり、作成者の主張を裏取りなしに事実として断定したりしない（`BR006` FAIL）。
- **4 つの働き・時制の峻別**: 語尾を散らす目的で文の働きや時制を変えず、次の 4 区分を書き分ける。

| 区分 | 文末の形（敬体既定） | 用例 |
|---|---|---|
| **この PR の変更事実（Diff 確認済み）** | 〜を変更しています / 〜を追加しました | 期限切れ判定の境界条件と再試行上限を改めています（予定表現の「〜する予定です」にしない） |
| **変更後のシステム仕様・実動作** | 〜を返します / 〜を検証します | 再取得に失敗した場合は `401 Unauthorized` を返します |
| **既存コードの前提・従来仕様** | 従来は〜する実装でした / 〜を必須としています | 従来は期限切れエラーをすべて `302` リダイレクトへ流していました（Diff にない経緯を想像で作らない） |
| **PR 説明文の主張・未確認事項** | PR 説明文では〜と記載されていますが、コード上では〜 / 〜は未確認です | PR 説明文では全テスト通過と記載されていますが、ローカルテストの実行可否は未確認です |

### 1.3 十分な言葉の説明（行番号実況の禁止 × 背景・仕組み・挙動変化の言語化）

- **機械的な行番号・手順実況の禁止**: 「`auth.py` の 5 行目を編集し、12 行目に `if` 文を追加しました」のように、Diff をそのまま音読しただけの作業実況は読み手の理解を助けないため書かない。
- **言葉を削りすぎない丁寧な解説**: 窮屈な行数制限で背景を端折ったり、Mermaid 図だけを裸で置いたりしない（`BR002`, `BR010`）。**「従来何が問題だったか（背景）」「どこをどのような仕組みに変えたか（構造変化）」「結果として外から見た動きがどう変わったか（振る舞い変化）」** を自然な言葉で過不足なく説明する。

### 1.4 意味の保持 4 原則（`/yomiyasu` 最優先ルール）

1. **主張**: Diff と資料が示す要点と論理関係（何が・なぜ変わったか）を保ち、論点を別の概念にすり替えない。
2. **比重**: 否定対比（「A ではなく B」）の A を並列や優先順位（「A に加えて B」「まず A」）へ変えない。比較表現では比較対象と差の基準を残し、中身のない修辞（「魔法ではなく〜」）だけを肯定文に改める。
3. **言い切りの強さ**: 可能性・推量（「〜場合があります」）、許可（「〜してよい仕様です」）、能力（「〜できます」）、義務（「必須です」）、保証の強さをコード上の事実以上に引き上げない（「必ず防げます」「今後エラーは起きません」を勝手に足さない）。
4. **文の働き**: 事実の説明・設計意図・確認ポイントの提示・未確認の留保を混ぜない。

### 1.5 補助動詞・形式名詞のひらがな化（`BR016` 対応）

補助動詞と形式名詞の漢字「事」「為」はひらがなに統一する。

- 対象例: `して下さい` → `してください` / `出来ます` → `できます` / `して頂く` → `していただく` / `して見る` → `してみる` / `する事` → `すること` / `する為` → `するため`（`BR016` WARN）。
- 除外対象: 実質的な意味を持つ名詞（「事の経緯」「為替」）、コード識別子、ファイルパス、引用文字列。

### 1.6 不要読点の排除と残すべき読点

| 扱い | 対象となる箇所 | 具体例 |
|---|---|---|
| **削除する** | 短い主題・主語・目的語（6 字以内目安）の直後、否定対比「なく」の直後、見出し内の読点、短い語句の連続読点 | 「この PR は、設定を、変更しています」→「この PR は設定を変更しています」<br>「A ではなく、B」→「A ではなく B」 |
| **残す** | 外すと掛かり先が変わる所、主題のあとに別の主語が続く所、長い主語や条件節のあと、逆接・理由・並列の切れ目、文頭接続語（ただし、また、）のあと | 「この画面では、担当者が件数を入力します」<br>「トークンが期限切れの場合は、401 を返します」 |

- 否定と肯定を 2 文に分けた型（「目的は高速化ではありません。重複送信を防ぐことです。」）は、後ろの文が別主張や根拠補足でない限り「目的は高速化ではなく重複送信を防ぐことです。」と 1 文へ統合する。Mermaid コードブロック・引用・表セル・インラインコード内は対象外とする。

### 1.7 比喩動詞・擬人化・直訳語（calques）の具体動作化

- **禁止する比喩動詞・曖昧語**: 「安全側に倒す」「地味に効く」「静かに壊れる / 黙って失敗する」「バグを潰す」「時間を溶かす」「深く踏み込む」「例外を上に逃がす」は使わず、コード上の実動作（例外を送出する、通知を出さずに処理を打ち切る、呼び出し元へ再送出するなど）で書く。
- **擬人化の境界**: コードや仕組みに感情・意志・人の役目を持たせる表現（「呼び出し元の事情を知っている」「ルーターが交通整理を引き受ける」）は避け、何を受け取り・何を呼び・何を返すかを書く。一方、開発者（`expert`）向け解説として **識別子・クラス・モジュールが主語の文**（`AuthMiddleware` が `401` を返します、`retry_limit` が再試行上限を決めます）と定着した技術表現（テストが通る、キャッシュが効く）は維持する。
- **直訳語・1 字漢語訳・漢語詰まり・連用形 1 語名詞の回避**: 「ジョブが拾う」「接続が入口を通る」などの直訳表現は「キューから取得する」「API エンドポイントで受信する」へ改める。英語術語への不自然な 1 字漢語当て（今回の「版」→ バージョン、対象の「枝」→ ブランチ、PR の「題」→ タイトル、配列の「頭」→ 先頭）や硬い直訳語（「背景実行」→ バックグラウンド実行、「根因」→ 根本原因、「時間窓」→ 集計期間、「偽緑」→ 誤成功）、助詞落ちの漢語詰まり（「認証失敗時エラー返却」→「認証失敗時はエラーを返します」）、連用形 1 語名詞（「結果の確かめ」→「結果の確認」）を避ける。ただし「確認する」「使用する」「停止する」「動作する」「発生」「復旧」など技術文書で自然な漢語は無理に和語へ崩さない。

### 1.8 分類ラベル太字箇条書き禁止・太字抑制・`expert` 前提（`BR015` 対応）

- **禁止（分類ラベル＋説明文）**: `- **変更点**: 認証フローを見直しました` や `- **改善点**: TTL を短縮しました` のように、説明文をまとめた分類ラベル＋コロンは **1 件でも禁止**する（`BR015` FAIL）。太字とラベルとコロンを外し、意味を文中に織り込んで 1 文にする。
- **維持（値ラベル＋値・識別子）**: `- 対象ファイル: src/auth.ts` や `> 🎯 Scope: ...`、`- 依存追加: pydantic（リクエスト境界の型検証のため）` のようにコロンの後ろが値や対象名である項目は、**太字を付けずに**残す。
- **太字抑制**: 300 字超かつ 1,000 字あたり 3.0 個超で出る `excess_bold` 警告を防ぐため、地の文や表セル内での `**...**` 多用を控える（目安は 1,000 字あたり 2 個以下）。描画が崩れる記号隣接太字（`**「語」**` や ``**`code`**``）も使わない。
- **`expert` 読者前提**: レビューする開発者（`expert`）を前提とし、TTL・JWT・N+1・冪等性などの基本技術用語に教科書的な注釈を足さない（例外は新規追加・更新された依存パッケージの導入理由 1 行のみ）。

## 2. 構造バッジ 4 種の許可位置と見出し規則

`/yomiyasu` は原則として絵文字を警告対象とする一方、本スキルはトリアージ階層の視認性を高めるために 4 種の構造バッジのみを限定使用する。Text-Only Mode との 1 対 1 置換表は [mermaid-and-templates.md](mermaid-and-templates.md#2-text-only-モード仕様--badge-mode-text) を参照。

1. **装飾絵文字の全面禁止（全モード共通、`BR014`）**:
   - 地の文、セクション見出し、箇条書き、比較表（`◎ / ○ / △ / ×`）で `🚀 / ✨ / 🔥 / ✅ / ⚠️ / 💡 / 🎉` 等の装飾絵文字を使うことは禁止する。
2. **Visual Badge Mode（既定: `auto` / `emoji`）での許可位置**:
   - `🎯`: `> 🎯 Scope: ...` 行頭、および `### 🎯 読むべきファイル` 見出し行頭のみ。
   - `🧠`: `🧠 Must-Read` ラベル先頭のみ。
   - `👀`: `👀 Skim` ラベル先頭のみ。
   - `⏭️`: `⏭️ Safe-to-Skip` ラベル先頭のみ（`<summary>` 内を含む）。
3. **Text-Only Mode（`--badge-mode text`）への切替条件**:
   - ①ユーザーが「絵文字なし」「テキスト表記」等を指定した場合、または ②リポジトリ内の `CLAUDE.md` / `AGENTS.md` / `.yomiyasu-words/` に絵文字禁止ルールがある場合は、自動的に `--badge-mode text`（`[SCOPE]`, `[TARGET]`, `[MUST]`, `[SKIM]`, `[SKIP]`）へ切り替える。
   - 同一解説内で絵文字バッジとテキストバッジを混在させてはならない（`BR014` FAIL）。
4. **セクション見出し規則**:
   - 標準テンプレートのセクション構成（`## 全体像（なぜ・何を変えたPRか）`, `## 仕組み・処理フロー`, `## 主な変更ポイントと設計判断`, `## 読む順番ガイド`, `## 注意・確認ポイント`）に沿い、末尾に中身のない `## まとめ` 見出し（`short_summary_heading`）を足さない。
   - 見出しの中に読点、「A ではなく B」の形、結論や警告の長文を詰め込まない。
   - `yomiyasu_lint.py` は 8 字以下の見出し語が本文に再登場しないと `metaphor_label`（`info`）を出す場合があるが、標準テンプレート見出しへの指摘はポストフィルタで除外する（§4 参照）。

## 3. Chat PR 解説向け AI クリシェ 12 類型言い換え辞書と Good / Bad 7 例

### 3.1 AI クリシェ 12 類型言い換え辞書（`BR005` / `BR006` 対応）

PR 作成者の説明文に以下のクリシェが含まれていてもそのままオウム返しせず、必ず実際の Diff から具体的な条件・型・挙動を読み取って言い換える。

| # | 禁止 AI クリシェ（例） | 読み手に伝わらない情報 | Chat 解説での具体的な言い換え先 |
|---|---|---|---|
| 1 | **堅牢性を向上 / 安定性を強化** | どの異常をどう防ぐか不明 | 異常入力の条件・再試行上限・タイムアウト秒数・返却ステータス |
| 2 | **クリーンで保守性の高い設計 / 可読性を向上** | 構造変化の軸が不明 | 分離した責務・廃止した重複処理・抽出したインターフェースと依存方向 |
| 3 | **シームレスに統合 / スムーズに連携** | 境界とエラー伝播が隠れる | モジュール間の受け渡し型・境界インターフェース・失敗時の伝播範囲 |
| 4 | **包括的なエラーハンドリング / 適切に処理** | 握りつぶしか再送出か不明 | 捕捉する例外型・ログ出力レベル・返却ステータスまたは再送出の有無 |
| 5 | **パフォーマンスを大幅に最適化 / 劇的に高速化** | 計算量・クエリ変化が不明 | 変更したクエリやアルゴリズム構造（N+1 解消、索引追加等）と確認可能な根拠 |
| 6 | **柔軟な対応 / 将来の拡張性を見据えた設計** | 今回の変更範囲がぼやける | この PR で実際に切り替わる設定項目・分岐・現在の利用箇所のみ |
| 7 | **エッジケースを網羅 / リスクを未然に防止** | 「網羅」は検証不能な誇張 | 実際に分岐やテストが追加された具体条件（`null`・空配列・0 件・競合等） |
| 8 | **〜という挙動を排除 / 静かに壊れるのを防ぐ** | 検知・停止の仕組みが不明 | どの条件で処理を中断し、どの例外またはエラーステータスを返すか |
| 9 | **開発者体験（DX）の向上 / 直感的な API** | 型や呼び出し方の変化が不明 | 変更された引数型・デフォルト値・エラーメッセージの具体内容 |
| 10 | **全体の整合性を担保 / 一貫性を確保** | トランザクション境界が不明 | DB トランザクション範囲・ロック対象・一意制約の対象テーブル |
| 11 | **機械的な行番号・手順実況** | Diff の行番号や手順の朗読 | **なぜ必要だったか（背景）** と **意味単位の仕組み変化・外部挙動の変化** |
| 12 | **コード削減量・作業量の代弁自慢**（`BR006`: `不要コードを200行削減` 等） | 宣伝調で読解の助けにならない | 作成者の自慢表現は省き、Scope バナーの客観数値と注目箇所の案内に徹する |

### 3.2 Chat PR 解説の Good / Bad 7 パターン比較例

#### パターン 1: 全体像 — 認証不具合修正 PR の解説

- **Bad**: `このPRは、認証モジュールの堅牢性を向上させ、包括的なエラーハンドリングを実現する為の修正です。verifyToken の15行目に if (!token) return null を追加し、呼び出し元でも安全側に倒すようにしています。`
  - 違反点: 「このPRは、」の不要読点、クリシェ 2 種、形式名詞「為」の漢字（`BR016`）、行番号の機械的実況、比喩動詞「安全側に倒す」。
- **Good**: `認証トークンの期限切れ時に 401 を返さず再ログイン画面へ無限リダイレクトしていた不具合を修正する PR です。期限切れ判定の境界条件と再取得の試行上限（1回）を改め、リフレッシュ失敗時は即座にセッションを終了してログイン画面へ戻す動きに変わっています。`

#### パターン 2: 全体像 — クエリ性能改善 PR の解説

- **Bad**: `一覧取得APIを大幅に最適化し、パフォーマンスを劇的に高速化したPRです！シームレスな統合により、スケーラブルなデータ取得を実現しています。`
  - 違反点: 根拠のない誇張クリシェ（`BR005`）、感嘆符による煽り、「シームレスな統合」。
- **Good**: `注文一覧 API で顧客情報を 1 件ずつ遅延取得していた N+1 クエリを、JOIN による一括取得へ変更する PR です。1 リクエストあたりの SQL 発行回数がレコード件数に比例しない構成へ変わり、レスポンスの JSON 構造とソート順は既存仕様のまま維持されています。`

#### パターン 3: 仕組み・処理フローの補足 — 非同期ワーカー PR の解説

- **Bad**: `ワーカーが静かに壊れるバグを潰しています。タイムアウト処理に深く踏み込んで、柔軟なリトライ仕組みを導入して、信頼性を改善。`
  - 違反点: 比喩動詞（「静かに壊れる」「潰す」「深く踏み込む」）、曖昧語（「柔軟な」）、`て` 形の体言止め。
- **Good**: `従来の Webhook 送信ワーカーは外部通信のタイムアウト時に例外を握りつぶしていたため、未送信に気づけない状態でした。この PR では 30 秒超過時に失敗ログを出力して遅延キューへ再登録し、最大 3 回の再送後も失敗した場合は dead-letter テーブルへ記録するフローに改めています。`

#### パターン 4: 変更ポイント箇条書き — 分類太字ラベルの排除と値ラベルの保持

- **Bad**:
  ```markdown
  - **改善点**: 認証フローをクリーンで保守性の高い設計へ刷新しています。
  - **修正点**: `verifyToken` の実装を見直しています。
  - **注意点**: 再試行回数の挙動が変わります。
  ```
  - 違反点: 分類太字ラベル箇条書き（`BR015` FAIL）、クリシェ（`BR005` FAIL）、具体動作の欠落。
- **Good**:

## 4. `pr_briefing_lint.py` と `yomiyasu_lint.py` の連携・ポストフィルタ仕様

### 4.1 `/yomiyasu` 未導入環境での単体動作保証

本スキルは外部スキル `/yomiyasu` への必須依存を持たない。`/yomiyasu` がインストールされていない環境でも、本ドキュメント（§1〜§3）と同梱スクリプト `scripts/pr_briefing_lint.py`（`BR001`〜`BR016`）だけで、Chat PR 解説の構造・Mermaid 安全性・AI クリシェ・作成者モード混同・絵文字衛生・分類太字ラベル・補助動詞漢字を自己完結で検査できる。

### 4.2 `/yomiyasu` 導入済み環境での連携仕様

1. **動的探索と実行コマンド**:
   - `pr_briefing_lint.py --yomiyasu-lint` 指定時は、標準配置先（`../yomiyasu/scripts/yomiyasu_lint.py`, `~/.agents/skills/yomiyasu/scripts/yomiyasu_lint.py`, `~/.gemini/config/skills/yomiyasu/scripts/yomiyasu_lint.py`, `~/.claude/skills/yomiyasu/scripts/yomiyasu_lint.py`）の順に探索し、存在すれば次を実行する（未導入時はエラーにせず無言スキップ）。
   ```bash
   python3 "<yomiyasu_dir>/scripts/yomiyasu_lint.py" --doc-type pr --reader expert --json - < briefing.md
   ```
2. **呼び出し時の必須ルール**:
   - **`yomiyasu_check.py` は使わない**: 推敲レポート用の固定見出し（`### 書き直した本文` 等）を要求し、Chat PR 解説フォーマットと衝突するため。
   - **`--doc-type pr --reader expert` を必ず指定する**: `pr` 種別により箇条書き比率警告（`excess_list`）が自動除外され、`expert` 指定により識別子主語の技術文が適切に保護される。
   - **`--strict` や `--fail-on=warn` を直接渡さない**: Visual Badge Mode の構造バッジ 4 種が `emoji_prohibited`（`warn`）に該当するため、JSON 出力を受け取ってポストフィルタを適用してから合否を判定する。
   - 対象リポジトリの最上位に `.yomiyasu-words/`（`allow.txt`, `flag.txt`, `flag-patterns.txt`）がある場合は `yomiyasu_lint.py` が自動参照するため、プロジェクト固有の用語ルールも反映される。

### 4.3 検査責務分担とポストフィルタ規則

| 検査領域 | 主担当（常時: `pr_briefing_lint.py`） | 補完担当（任意: `yomiyasu_lint.py`） | ポストフィルタと衝突回避 |
|---|---|---|---|
| **Chat 解説構造・規模・読む順・依存説明** | `BR001`〜`BR004`, `BR011`〜`BR013` | 対象外 | 責務完全分離（重複ゼロ） |
| **Mermaid 安全規約・言語補足必須** | `BR007`〜`BR010` | 対象外 | `pr_briefing_lint.py` 単体で保証 |
| **AI クリシェ・作成者モード混同防止** | `BR005`, `BR006` | 対象外 | `pr_briefing_lint.py` 単体で保証 |
| **分類太字ラベル・補助動詞漢字** | `BR015`, `BR016` | `bold_label_list` | 値ラベル（`- 対象ファイル: ...` 等）は太字を外して誤反応を防ぐ |
| **絵文字衛生・構造バッジ制御** | `BR014`（モード別許可・混在禁止） | `emoji_prohibited` | `--badge-mode text` 時は全件 FAIL。Visual Badge Mode 時は **許可構造バッジ（`> 🎯 Scope:`, `### 🎯 読むべきファイル`, `🧠 Must-Read`, `👀 Skim`, `⏭️ Safe-to-Skip`）のみを含む行** の `emoji_prohibited` を除外し、装飾絵文字のみ警告する |
| **深層日本語表現・読点・直訳語** | 重複実装しない | `pause_comma`, `metaphor_verb`, `calque`, `ai_phrase`, `renyo_noun`, `bold_not_rendered`, `excess_bold` | `/yomiyasu` 導入時のみ検査精度を上乗せする |
| **セクション見出し** | `BR001`（冒頭全体像） | `metaphor_label`, `short_summary_heading` | `short_summary_heading`（「まとめ」見出し禁止）は有効化。`## 読む順番ガイド`・`## 注意・確認ポイント`・`## 検証・確認ポイント` 等の標準見出しへの `metaphor_label` はポストフィルタで除外する |

- **出力汚染の厳格抑止**: `yomiyasu_lint.py` を連携実行した場合でも、`/yomiyasu` 固有の報告見出し（`### 書き直した本文`、`### 変えたところ`、`### 確認の記録`、`yomiyasu-check:` 行）は Chat 解説出力に一切含めない。
