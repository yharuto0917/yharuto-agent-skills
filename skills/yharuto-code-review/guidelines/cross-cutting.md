# 横断レビュー基準（Stage 3 常時適用）

Stage 3 の本レビュー開始時に必ず読み込む横断基準である。差分の表面的な変更行だけを追わず、危険な変更兆候の精読、実環境（HTML・CSS・DB）とテストモックの突き合わせ、ビルドハッシュ設定の照合、同種既存実装との比較による欠落発見を順に行う。

## 1. 精読シグナルと流す条件

ファイル行数の大小だけで優先度を決めず、損害が大きい領域から精読する。小さくても認証・認可の判定箇所や境界変換は最優先で読み、定型的な宣言の羅列や未改変の生成物は確認後に流す。

| 精読シグナル | 何を確認するか | 精読する理由 |
|---|---|---|
| 一意性・順序・連番の自前計算 | `count + 1` 採番やアプリ側の事前重複確認だけで一意性を保とうとしていないか | 並行リクエストで同じ採番や重複登録が発生するため |
| 待機が曖昧な非同期副作用 | ループ内の非同期コールバックや未待機の Promise・タスクがないか | 完了順序の逆転や例外の未検知が起きるため |
| トランザクション外の読み書き | 値を読み取り、加工して書き戻す処理がロックやトランザクションの外にないか | 同時実行で片方の更新が上書き消失するため |
| 認証・認可判定の見当たらなさ | ハンドラ先頭や変更操作の前に認証・権限・テナント確認が存在するか | 防御の欠落は差分行に現れず能動的に探す必要があるため |
| 外部入力の特権操作・境界流入 | クライアント入力が管理操作、クエリ構築、URL、ファイルパスへ流れていないか | 未検証の識別子やパスが権限昇格や情報流出を生むため |
| 金額・数量・重量換算・日時の計算 | 最小単位、端数丸め規則、境界値（`0`・上限）、タイムゾーンの扱い | わずかな計算ズレが金銭や在庫の実損につながるため |
| 秘密情報・環境設定・通信先URL | 鍵、トークン、公開環境変数、送信先オリジンの変更 | 一度外部へ露出・誤送信すると回収できないため |
| 対になる実装や連番・同型モジュール | コピペ由来の兄弟コンポーネントや対称処理の片方だけ修正されていないか | 片方に旧仕様や識別子の取り違えが残りやすいため |

次の2条件を満たす箇所は深入りせず流してよい。

- 自動生成ファイルや外部テンプレート由来であり、手作業の改変がないことを差分で確認できた箇所（改変行があれば精読対象に戻す）。
- 外部入力・状態更新・金銭計算・権限判定を一切伴わない静的な文言や定数定義の羅列。

## 2. 実コード・画面構造・DBスキーマとテストモックの横断照合

Stage 1 を通過し Stage 2 の単体テストが成功していても、テスト通過だけを根拠に安全と判断しない。JSDOM や簡易スタブは実ブラウザの描画切り抜きや実 DB の制約を再現しないため、変更箇所では必ず実コードとテストモックの双方を開いて次の4点を突き合わせる。

| 横断照合の軸 | 突き合わせる対象 | 単体テストを素通りする典型不具合 |
|---|---|---|
| HTML要素階層とDOM操作範囲 | コンポーネントが出力する親子・兄弟構造と、クライアント処理が参照するセレクタ・要素 | ブラウザ固有のビューポート占有APIやレイヤー表示APIの対象に内側の部分要素だけを指定し、外側の兄弟要素にある操作部品や通知欄が実ブラウザでは描画対象外に隠れて操作不能になる不具合（JSDOM では描画領域の切り抜きが起きず通過する） |
| CSS配置と表示状態切り替え | `overflow: hidden`、`transform` 等が作る包含ブロック、`z-index` の重なり順、背面スクロール固定スタイル | モーダルやドロップダウンメニューが親枠で切り抜かれる、背面へ隠れて押せなくなる、または閉鎖後に背面スクロール固定が残る不具合 |
| DBスキーマ・API型と模擬データ | マイグレーション・スキーマ定義の型・単位（最小整数単位と小数単位、ケースと個数、NULL許容）とテストのスタブ値 | 模擬データが実スキーマの単位や必須列と食い違ったままテストが成功し、本番データで計算誤りや制約違反が起きる不具合 |
| 実行順序と初期状態の前提 | 実環境の遅延読込・SSR初期出力・別タブ更新と、テスト内の同期的な初期セットアップ | テストでは最初から揃っている要素やストレージ値が、実ブラウザの初期描画時点では未生成で例外や空表示になる不具合 |

## 3. 差分ビルド・キャッシュのハッシュ入力更新漏れ

新しいファイル種別、テンプレート、スタイル、設定ファイル、クライアント資産、環境変数参照を追加または移動した変更では、`impact_scan.py` が出力する `build_hash_configs`（差分ビルド判定、キャッシュキー計算、バンドラ設定、CI キャッシュ設定、ETag 生成処理）を必ず開いて照合する。

1. ハッシュ計算や変更検知の対象パターン（拡張子・ディレクトリ一覧・依存グラフ入力）に、今回追加・移動したファイル群が含まれているかを確認する。
2. 出力結果を左右する環境変数や設定キーを増やした場合、その値がビルドキャッシュや配信キャッシュのキー入力に含まれているかを確認する。
3. 対象から漏れている場合、ソースコードや設定を更新しても古いビルド成果物が再利用されて変更が反映されないため、影響度に応じて `🔴 Bug` または `🟡 Risk` として報告する。

## 4. 同種既存実装との比較による欠落監査（Negative Space）

差分行だけを読むと「書かれるべき処理が最初から存在しない欠落」を見落とす。新規エンドポイント、画面操作、イベント購読、バッチ処理の追加・変更時は、`impact_scan.py` の `comparative_files` に挙がった同種の既存実装を1〜2ファイル開いて横並びで比較する。

1. 同種ハンドラにある認証ミドルウェア、ロール判定、テナント・所有者絞り込み条件が抜けていないかを確認する。
2. 入力スキーマ検証、レート制限、冪等キー確認、監査ログ出力が既存実装と同じ水準で備わっているかを確認する。
3. イベント購読やタイマーの解除、ロックや一時ファイルの解放、在庫減算や枠消費に対するキャンセル時の復元処理が対になっているかを確認する。
4. ロケール・表示設定同期、認証状態監視、ウィンドウ間メッセージ受信などの既存共通処理を無視して別系統の処理を重ねていないかを確認する。

## 5. 作用する実行局面と影響しない範囲の特定

変更関数とその呼び出し元（`impact_scan.py` の `symbols` 参照箇所）をたどり、今回の変更がどの実行局面（ビルド時、サーバーリクエスト処理時、SSR 初期出力、ブラウザ初期描画・操作時、バックグラウンドジョブ）で動き、どの機能や経路には一切影響しないかを事実として確定させる（選別および未確定仕様・変更外既存バグの扱いは `references/judgment.md` に従う）。
