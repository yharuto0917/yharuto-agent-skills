# 依存関係・ロックファイル変更レビュー基準

マニフェスト（`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod` 等）またはロックファイル（`pnpm-lock.yaml`、`package-lock.json`、`yarn.lock`、`uv.lock`、`poetry.lock`、`Cargo.lock`、`go.sum` 等）が変更されたときに読み込む基準である。依存変更はコード差分が小さくても本番クラッシュ、ビルド再現性の喪失、サプライチェーン侵害を引き起こすため、マニフェスト・ロックファイル・実コード参照箇所を横断して確認する。

## 1. マニフェストとロックファイルの整合性

1. マニフェストの依存追加・削除・バージョン指定変更に対し、対応するロックファイルが同じ PR 内で同期更新されているかを確認する。片方のみの変更は CI の `--frozen-lockfile` / `npm ci` 失敗や開発環境ごとの解決バージョン不一致を招くため `🔴 Bug` または `🟡 Risk` として報告する。
2. 変更意図と無関係な大量パッケージの更新、ロックファイル形式バージョンの意図しないダウングレード、複数パッケージマネージャのロックファイル混在（例として `pnpm-lock.yaml` 管理リポジトリへの `package-lock.json` 誤追加）がないかを確認する。
3. 取得元レジストリ URL の書き換え（非公式ミラー、個人 Git リポジトリ、`file:` / `link:` ローカルパス残存）や、整合性ハッシュ（`integrity` / `go.sum`）の欠落がないかを確認する。
4. 本番実行時に参照されるパッケージが誤って `devDependencies`（または開発専用グループ）に置かれて本番コンテナで `Cannot find module` / `ModuleNotFoundError` を起こさないか、逆にテスト・ビルド専用ツールが本番依存に混入していないかを確認する。

## 2. 破壊的変更・ピア依存・重複解決の確認

1. メジャーバージョン更新（`0.x` 系のマイナー更新を含む）では、`impact_scan.py` やコード検索でリポジトリ内の該当パッケージ利用箇所を洗い出し、廃止 API、引数・戻り値型、デフォルト設定値、例外送出条件の変更に追従できているかを確認する。
2. フレームワーク・コンパイラ・プラグイン群（React、Next.js、Vite、TypeScript、Pydantic、ORM 等）の `peerDependencies` や要求ランタイムバージョン（`engines.node`、`requires-python`、Rust `rust-version`、Go ディレクティブ）と矛盾がないかを確認する。
3. ステートフルな共有パッケージ（React 本体、ルーター、GraphQL、OpenTelemetry、認証 SDK、ORM 等）がロックファイル内で複数バージョンに重複解決され、`instanceof` 判定の失敗や Context・シングルトンの分断を起こしていないかを確認する。

## 3. 推移的依存とサプライチェーン安全性

1. 新規追加パッケージの名前誤認（タイポスクワッティング）、長期間保守が停止したパッケージ、数行で書ける処理に対する過剰な推移的依存の引き込みがないかを確認する。
2. `postinstall` / `install` スクリプトやネイティブビルドフックを持つ依存が追加された場合、正当な用途かを確認する。外部フォーク PR（`is_fork_pr == true`）、`--untrusted` 指定時、または `ci_script_hazard`（`package.json` の `scripts`・`Makefile`・`pyproject.toml`・`build.rs`・`.cargo/config.toml` への危険コマンド追加）該当時の依存やスクリプト変更は任意コード実行経路になりうるため厳重に精読する。
3. セキュリティ修正を含むバージョンからの意図しないダウングレードや、脆弱バージョンへの固定ピン留めが行われていないかを確認する。
4. バンドラ・ビルド対象ファイルを増減させる依存変更では、`build_hash_configs` のキャッシュキー入力（ロックファイルハッシュ等）が正しく連動するかも確認する。

## 4. バンドルサイズ・実行環境互換・ライセンス影響

| 点検観点 | 危険シグナル | 求める修正方針 |
|---|---|---|
| クライアントバンドル肥大化 | Tree-shaking が効かない全量インポート専用パッケージの追加、またはクライアント側コードからのサーバー用巨大 SDK 参照 | サブパスインポート対応パッケージへの切り替え、動的 `import()` 分割、またはサーバー側処理への隔離を行う |
| SSR / Edge / ブラウザ互換欠如 | Edge Runtime、Cloudflare Workers、ブラウザ経路で動くモジュールへの Node.js 専用 API（`fs`、`net`、`child_process`、ネイティブ C++ アドオン）依存の混入 | Web 標準 API 互換パッケージへ変更するか、Node.js 専用ランタイム経路へ分離する |
| ライセンス不適合 | 商用・プロプライエタリ製品や MIT/Apache 公開ライブラリへの強いコピーレフト（GPL / AGPL 等）や商用制限ライセンス依存の新規追加 | プロジェクトの配布形態と適合するライセンスの代替手段へ置き換えるか、法務・ライセンス方針の確認を求める |
