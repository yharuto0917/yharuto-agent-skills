# AI Slop・保守構造監査基準（SSoT）

コード変更を含むレビューで読み込む AI Slop（表面上は動作しても保守時の欠陥や異常隠蔽を招く低品質実装）の単一基準書である。`scan_diff_smells.py --session` が出力する候補行は調査の手がかりであり点数ではない。必ず周囲の実コード、優先順位階層（`P0`〜`P5`）、免除条件（Waiver）、5つの関数型変換禁止例外に照らして採否を決め、候補が検出された（`smell_count > 0`）うえで免除とする項目は `<session_dir>/draft_findings.json` の `dismissed_smells` に10文字以上の具体的根拠を記録する。

## 1. 優先順位階層（P0〜P5）

構造改善や簡素化の提案を検討する際は上位の階層を優先し、上位項目を1つでも損なう提案は棄却する。

1. `P0`（振る舞い・実行特性・公開仕様の保持）では、入出力、境界値（`0`・`""`・`NaN`・`null`）、例外伝播、`await` の直列・並列順序、React Hooks の呼び出し順序、リソース解放、計算量オーダー（`O(N)` から `O(N^2)` への悪化禁止）、既存の `export` シグネチャや公開 API・JSON キー名を維持する。
2. `P1`（リポジトリ規約と言語標準イディオム）では、ベースブランチ側 `REVIEW.md` の方針と各言語の標準的な書き方（Go での `for range` と明示的エラー返却の維持など）を優先する。
3. `P2`（信頼境界での型検証と浅い制御フロー）では、外部入力を境界で一度だけ検証・型変換し、内部処理では不要な防御ネストや広域 `try/catch` を排してガード節で平坦化する。
4. `P3`（単一実装と宣言的コレクション操作）では、二重実装を排し、第3節の5例外に当たらない限り可変カウンタや空配列への `push` 蓄積を標準のコレクション操作へ置き換える。
5. `P4`（役割と振る舞いが一致する命名）では、副作用の有無が動詞と一致し、公開仕様を変えない範囲で役割を表す名前を選ぶ。
6. `P5`（行数の短さ）は最低優先とし、`P0`〜`P4` を犠牲にするワンライナー圧縮やネスト三項演算子は提案しない。

## 2. AI Slop 6観点の4列判定表

各観点について、検出シグナルが実コードで確認でき、かつ右列の免除条件（Waiver）に当たらないものだけを `🟡 Risk`（現実に誤動作・未定義参照・値不一致・データ欠損を引き起こす場合は `🔴 Bug`）として報告する。

| 1. 処理の二重実装 | 同一ファイルや別モジュールに型付きの純粋関数があるのに、生文字列スクリプト、HTMLテンプレート、別ハンドラ内で同じ計算やURL組み立て、保存値解決を書き直している | 生文字列や別箇所での再実装を削除し、既存の型付き純粋関数または単一の共通モジュールを参照する構成へ一本化する | 実行環境が物理的に分離されコード共有が不可能な外部境界で、自動テストにより双方の出力一致が検証されている最小限の定数定義 |

## 3. 関数型変換を提案してはいけない5つの禁止例外

手続き的なループを見つけても、次の5ケースのいずれかに該当する場合は通常のループ（`for` / `for...of` 等）の維持が正しく、高階関数やパイプラインへの書き換えを提案してはならない。

1. 直列 `await` を伴うループ（`for (const x of xs) { await send(x); }`）に対し、`Promise.all(xs.map(...))` や `xs.forEach(async ...)` への変換を提案しない。`forEach(async)` は Promise が待機されず失敗を見逃す不具合を生み、無断の `Promise.all` 化は同時実行数の急増（レート制限超過や DB 接続枯渇）と部分失敗時の挙動変化を招く。
2. 1パスで複数の集計状態を同時更新するループや、1回で消費されるイテレータ・ジェネレータ（Python のジェネレータ、`Iterator` 等）を複数回の `filter` / `map` へ分割する提案をしない。走査回数が増えるだけでなく、1パス目でイテレータが空になり2パス目以降で誤った結果を返す不具合を起こす。
3. スプレッド構文を伴う `.reduce()` でのオブジェクト・配列構築（`xs.reduce((acc, x) => ({ ...acc, [x.id]: x }), {})` や `[...acc, x]`）を提案しない。反復ごとに全体コピーが発生して計算量が `O(N^2)` に悪化し可読性も下がるため、`Map`、`Object.fromEntries`、`Map.groupBy`、または通常のループを使う。
4. 外側関数からの早期 `return`、条件付き `break`、ジェネレータの `yield` を含むループを無理に高階関数へ押し込める提案をしない。
5. TypeScript / JavaScript で Nullish 除去のために `.filter(Boolean)` を提案しない。`0` や `""`、`NaN` といった正当な値まで消去され型絞り込みも効かないため、必ず `.filter((x) => x != null)` を指定する。

## 4. Slop監査と軽微改善提案の境界

- 上記6観点に該当する構造問題は `🟡 Risk`（現実に誤動作・未定義参照・データ欠損を引き起こす場合は `🔴 Bug`）として抽出し、コードベース全体の健全性（Code Health）判定へ反映する。
- 構造上の `🟡 Risk` には至らないが、今回の差分で変更されたコード行においてマジックナンバーの定数化、役割が伝わりにくい局所変数名の明確化、冗長な一時変数の整理など読みやすさを高める軽微な提案がある場合は、結論に影響しない `🔵 Nit` として出力する（ただし `P0`〜`P5`・第3節の5つの関数型変換禁止例外・`references/judgment.md` の6点不変条件を破る提案は `🔵 Nit` としても一切出さない）。
- リンターやフォーマッターが機械検出できる単純な書式・体裁のズレ、標準的な外部スタイルシートの読込など改善価値のない好み、未変更ファイルへの軽微指摘、および PR概要・PR本文・PRタイトルの更新漏れやコミットメッセージ等のコード外メタ事項は対象外とし、出力に一切含めない（Code Health 判定基準・スコープ境界・同種候補の集約は `references/judgment.md` に従う）。
