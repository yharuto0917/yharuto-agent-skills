# 並行性・データ整合・DBマイグレーション基準

非同期の初期化、ブラウザストレージ連携、DB 更新、ジョブ再実行、スキーマ変更を含む差分で読み込む基準である。単一リクエスト・同期モックの単体テストでは再現しない「同時実行」「再実行（リトライ・二重送信）」「途中失敗」の3場面で、状態や永続データに不整合が生じないかを確認する。

## 1. 初期化・DOM読込・非同期応答のタイミング競合

- スクリプト実行時点で対象 DOM 要素や外部スクリプトのグローバル変数が必ず存在する前提になっていないかを確認する。`defer` / `async` 属性、`DOMContentLoaded` 発火済み判定（`document.readyState === "loading"` 分岐の有無）、SPA の画面遷移・遅延マウントとの順序ズレで初期化が空振りしないかを見る。
- 検索入力、フィルタ変更、タブ切り替え等で非同期通信が連続発生した際、後から返ってきた古いリクエストの応答が最新の画面状態を上書きする競合（Stale Response）がないかを確認する。`AbortController` による前回通信の中断、またはリクエスト識別子による古い応答の破棄があるかを見る。
- 共有キャッシュやシングルトン初期化で、初回アクセスが同時に複数来た際に初期化処理や外部取得が多重実行されて状態が不整合にならないか（In-flight Promise の共有やロックの有無）を確認する。

## 2. 別タブ・複数ウィンドウ・ストレージ連携の競合

- `localStorage`、`sessionStorage`、IndexedDB、Cookie を使って表示設定、認証セッション、編集中データ、カート状態等を扱う場合、別タブでの更新通知（`storage` イベントや `BroadcastChannel`）と自タブ内の状態更新が噛み合うかを確認する。
- `storage` イベント受信時のハンドラが自タブで再度同じストレージ書き込みを発火させ、タブ間でイベント連鎖やちらつきを起こさないかを確認する。
- ストレージ上の JSON 配列・オブジェクトを「読み取って一部変更し全体を上書き保存する」処理が複数タブで同時に走ると、片方のタブの変更が消失する。キーの分割や書き込み直前の最新値取得・マージ方針が妥当かを確認する。

## 3. トランザクション外 Read-Modify-Write（TOCTOU）と排他制御

在庫数、口座残高、予約枠累計、利用上限枠、クーポン消化、連番採番などで「現在値を読み取り → アプリ側で上限判定や加減算を行い → 結果を書き戻す」処理がトランザクションや行ロックの外にある場合、同時リクエストで上限超過や更新消失（Lost Update）が起きるため `🔴 Bug` または重大な `🟡 Risk` として指摘する。

1. `UPDATE ... SET amount = amount + :delta WHERE id = :id AND amount + :delta <= :limit` のように 1 クエリ内で条件判定と更新を行い、更新件数（affected rows）で成否を判定しているかを確認する。
2. 複数ステップ更新が必要な場合にトランザクション内で `SELECT ... FOR UPDATE`（悲観ロック）またはバージョン列照合（楽観ロック）を用いているか、重複防止にアプリ側の事前 `SELECT` だけでなく DB 側の `UNIQUE` 制約を併用しているかを確認する。
3. DB トランザクションを開いたまま外部 HTTP API 呼び出しやメール送信、重いファイル処理を行い、コネクション枯渇やロック待ち連鎖を起こしていないかを確認する。複数行をロックする場合はデッドロックを防ぐためロック取得順序が一定かも確認する。

## 4. 冪等性と増減・登録/解除の対称性

- ネットワーク再試行、Webhook 再送、ジョブキューの再実行、ユーザーのボタン連打が起きた際、冪等キー（Idempotency Key）や状態遷移条件（`WHERE status = 'pending'` 等）によって二重決済・二重付与・二重送信が防がれているかを確認する。
- 状態を増減させる処理やリソースを確保する処理では、必ず対になる復元・解除処理が存在するかを確認する。
  - 在庫引当、ポイント消費、利用枠確保がある場合、注文キャンセル・決済失敗・タイムアウト時に元の数量へ戻す補償処理が漏れていないかを確認する。
  - イベント登録（`addEventListener`）、購読（`subscribe`）、タイマー（`setInterval` / `setTimeout`）、Observer、DB 接続、一時ファイル作成に対し、解除・クローズ処理が異常系を含めて対称に実行されるか（無名関数を渡したせいで `removeEventListener` が機能しない不具合がないか）を確認する。

## 5. SQLクエリ性能とマイグレーション安全性

スキーマ変更（マイグレーションファイル、ORM モデル定義）やクエリ追加がある場合は、稼働中環境への適用影響とデータ増加時の計算量を次の基準で確認する。

| 点検観点 | 危険シグナル | 求める安全な構成 |
|---|---|---|
| ロック拡大・無停止デプロイ阻害 | 大規模テーブルへの即時テーブル再構築や長時間排他ロックを伴う変更（ロック配慮なしの `CREATE INDEX`、段階を踏まない `NOT NULL` 制約追加、旧アプリ稼働中のカラム削除・改名） | 段階移行（NULL許容列追加 → 分割バックフィル → `CONCURRENTLY` や `NOT VALID` 検証分離での制約付与 → アプリ切替後の旧列削除）へ分割する |
| ロールバック不能な非互換変更 | データ削除・型縮小・列統合を伴い、デプロイ切り戻し時に稼働中コードが即座にエラーになる変更 | 新旧両バージョンのアプリケーションコードが同時稼働できる後方互換ステップを挟む |
| N+1 クエリと無制限全件取得 | ループ内部での個別 `SELECT` / API 呼び出し、`LIMIT` やページネーションを持たない大テーブル全件取得 | `IN` 句一括取得・`JOIN`・バッチローダーへの集約と取得上限の設定（ただし要素数が固定極小の設定表等に対する憶測の最適化指摘は行わない） |
| インデックスと検索条件の不整合 | 新規の `WHERE` / `JOIN` / `ORDER BY` 列に対応するインデックスがない、複合インデックスの先頭列を飛ばしている、または列側に関数を掛けてインデックスを無効化している | 実クエリの絞り込み条件と並び順に一致するインデックス構成を確認する |
