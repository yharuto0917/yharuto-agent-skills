# Go / Rust 監査基準

Go または Rust のコード変更時に読み込む基準である。各言語の標準イディオムを尊重して他言語流の誤った書き換え提案を防ぎつつ、並行処理・メモリ共有・エラー境界の重大不具合を検出する。

## 1. Go の標準イディオム尊重と誤指摘の防止

Go では明示的で単純な制御フローが言語標準であり、次の書き方に対して関数型化や抽象化の指摘を行ってはならない。

1. スライスの走査・絞り込み・変換を `for _, u := range users` と `if !ok { continue }` で書くのは Go の正規イディオムであり、自作ジェネリック `Map` / `Filter` 関数や無理なチェーン化を提案しない。
2. 各呼び出し直後の明示的な `if err != nil { return fmt.Errorf("...: %w", err) }` は標準のエラー伝播であり、重複削減を理由にエラー集約ラッパーや panic ベースの処理を提案しない（逆に `%v` でエラー型連鎖を切って呼び出し元の `errors.Is` / `errors.As` 判定を損なっている箇所は指摘対象とする）。
3. 狭いスコープでの短い識別子（`ctx`、`err`、`r`、`w`、`tx`、`i`）は Go の標準規約に沿っており、説明的な長名への改名を提案しない。

## 2. Go の並行性・defer寿命・スライス共有の危険地帯

1. 上流から受け取った `context.Context` を下流の DB・HTTP・gRPC 呼び出しへ渡さず `context.Background()` で置き換えてタイムアウトや切断が無効化されていないか、また `context.WithCancel` / `WithTimeout` が返す `cancel()` を `defer cancel()` で確実に呼んでいるかを確認する。
2. 起動した goroutine に終了経路があるかを確認する。受信側が早期リターンした後にバッファなしチャネルへ送信し続けて永久停止する goroutine リーク（`🔴 Bug`）、`sync.WaitGroup.Add` を `go func()` の内部で呼ぶ競合、ロックなしの共有 `map` 並行読み書き（ランタイム panic 発生）、ループ変数のアドレスやクロージャ参照の取り違え（Go バージョン設定確認を含む）を確認する。
3. `for` ループ内でファイルや `http.Response.Body`、DB `Rows` を開いて `defer Close()` すると関数終了まで全リソースが解放されず枯渇するため、反復単位の小関数へ分けるか各反復で閉じているかを確認する。併せて `rows.Err()` の確認漏れや、書き込みファイルの `Close()` が返すフラッシュエラー無視がないかを確認する。
4. 巨大スライスから切り出した部分スライスの長期保持によるメモリ残留、部分スライスへの `append` が元の基底配列を上書きして損なう不具合（`slices.Clone` や3引数スライス `s[a:b:b]` の要否）、および型付きの `nil` ポインタ（`var e *MyErr = nil`）を `error` インターフェースへ返して `err != nil` が真になる不具合（`🔴 Bug`）を確認する。

## 3. Rust の信頼境界エラー処理・非同期ロック・所有権

1. HTTP ハンドラ、RPC、パーサ、公開ライブラリ関数、常駐ワーカーの本番経路で、外部入力や I/O 結果に対して `.unwrap()`、`.expect()`、境界未確認の `slice[idx]`、文字列バイト位置スライス `&s[..n]`（マルチバイト文字境界 panic）を使っていないかを確認する。これらは `?` 演算子、`.get(idx)`、`char_indices`、`let ... else` による `Result` / `Option` 伝播へ改めるよう報告する（テストコード内や起動時の固定リテラル正規表現生成など不変条件が自明な `expect` は免除する）。
2. `std::sync::MutexGuard` や `RwLockGuard` を保持したまま `.await` を跨ぐとワーカースレッドのデッドロックや `!Send` エラーを引き起こすため、`.await` の前にブロックスコープを閉じてガードを drop するか、非同期 I/O 跨ぎが不可欠な場合のみ `tokio::sync::Mutex` を選ぶ。また `async fn` 内で同期ファイル I/O、`std::thread::sleep`、重い計算を直接呼んで非同期ランタイムを詰まらせていないか（`spawn_blocking` の要否）を確認する。
3. 所有権・借用・整数変換・`unsafe` 境界として、次の3点を確認する。
   - 読み取り専用の関数引数で `&str` や `&[T]` の借用を受け取れるのに所有型 `String` / `Vec<T>` を要求し、呼び出し元のホットパスで大容量データの不要な `.clone()` を強いていないかを確認する（`Arc::clone` や低頻度な小データの `.clone()` など性能に無影響な箇所への些末な指摘は除外する）。
   - `as` キャスト（`i64 as usize`、`u64 as u32` 等）による負数の巨大正数化や上位ビット切り捨てが境界入力で起きないか（`usize::try_from(...)` や `saturating_*` / `checked_*` の要否）を確認する。
   - `unsafe` ブロックが存在する場合、前提とする安全性不変条件が前後のコードで確実に満たされているか、可変参照のエイリアシング違反やダングリングポインタが生じないかを精読する。
