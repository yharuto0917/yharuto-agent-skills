# 名前付き構造改善処方箋（Structural Remedies）

構造や保守性の問題（`🟡 Risk` や `🔴 Bug`）を指摘する際は、「整理してください」のような曖昧な指示も、4行以上の修正コード全文の貼り付けも行わない。以下の処方箋から該当する構成を選び、対象リンク・本番コードの変更要点・テストやモックの修正要点を2〜3行の箇条書きで具体的に示す（提案前に `references/judgment.md` の6点不変条件を確認すること）。

## 1. ガード節による平坦化

- 適用場面: 4段以上の深い制御ネスト、ループ全体を覆う条件分岐、ネストした三項演算子により異常系や条件漏れが追いにくい箇所。
- 守るべき不変条件: React Hooks 呼び出しより前へ早期 `return` を動かさない。`finally`・`using`・`with`・`defer` なしでリソース解放前に抜けない。`NaN` や falsy 境界を変えない。
- 対象関数の先頭で無効入力や対象外状態を早期 `return`（ループ内なら `continue`）で返し、正常系の本処理を浅い階層へ平坦化するよう2〜3行で示す。
- ネスト三項演算子は条件ごとの明示的な分岐または名前付きの小関数へ分けるよう示す。

## 2. 条件分岐のディスパッチ表化・共有モジュールの責務分離

- 適用場面: 同じ種別キーに対する長い `if / else if`・`switch` の連鎖、または共有フォーマッタや共通ユーティリティに個別画面や特定テナント専用の装飾・条件分岐を継ぎ足している箇所。
- 守るべき不変条件: 既存の公開関数シグネチャと未定義キー入力時のフォールバックまたは例外挙動を維持する。
- 共有モジュールから個別機能専用の分岐を外し、呼び出し側または機能別の設定マップ（ディスパッチ表）・専用ラッパーへ分離するよう2〜3行で示す。
- 各分岐の差分テストを機能側の単体テストへ移し、共有モジュールの単一責務を保つよう示す。

## 3. 純粋計算とI/Oの分離・信頼境界への検証集約

- 適用場面: 外部I/Oを含まない内部計算を囲む過剰な `try/catch`、例外を破棄して空文字や `null` を返す空 `catch`、型エラー隠しの `as any` や無根拠な `?? ''` / `?? 0`、状態更新や通信を行う `get*`・`is*`・`validate*` 関数。
- 守るべき不変条件: 外部API・DB・ファイル・`JSON.parse` などの信頼境界で必要な1〜3行の例外捕捉や仕様上のエラー変換は削らない。既存の公開関数名は無断で変えない。
- 外部入力の型検証と例外捕捉をリクエスト受信箇所や境界アダプタ1箇所に集約し、内部処理の不要な `as any`・空 `catch`・不正フォールバックを削除して失敗時は呼び出し元へ例外を渡すよう2〜3行で示す。
- 数量や状態の計算ロジックを副作用のない純粋関数として切り出し、I/O処理や副作用を持つ関数には動作に合う動詞名を付けるよう示す。

## 4. `.toString()` 文字列化埋め込みの廃止と単一初期化スクリプト化

- 適用場面: 既存の型付き純粋関数があるにもかかわらず、HTML初期描画などに向けて `fn.toString()` や生スクリプト文字列・`new Function`・`eval` で同じ判定ロジックを二重実装して埋め込んでいる箇所。
- 守るべき不変条件: 初期描画時のちらつき防止（FOUC抑止）など、インライン実行が担っていた実行タイミング要件を損なわない。
- 関数の `.toString()` 文字列化埋め込みと生文字列内の再実装を削除し、ビルドと型検査を通した単一の初期化スクリプト（または `data-*` 属性による設定値受け渡し）へ一本化するよう2〜3行で示す。
- 初期描画時と通常モジュール実行時で保存値や設定の解決結果が一致する検証テストを追加するよう示す。

## 5. 既存共通同期フック・購読機構への統合

- 適用場面: 表示設定同期・リサイズ監視・認証状態購読・`window.addEventListener("message", ...)` などの共通処理がすでにあるのに、別コンポーネントで独自の監視処理を重ねて1回の操作でイベントや通信が多重発火している箇所。
- 守るべき不変条件: アンマウントや破棄時の登録解除（クリーンアップの対称性）と `origin` 等の通信境界検証を維持する。
- 新規に重複追加されたイベント監視・購読処理を削除し、既存の共通同期機構が提供するフックや購読関数を参照する構成へ統合するよう2〜3行で示す。
- 通信イベントを受信する共通ハンドラで送信元 `origin` とメッセージ形式を検証し、1イベントにつき処理が1回だけ走ることをテストで確認するよう示す。

## 6. 本番の過剰存在判定の削除とテストモック補完

- 適用場面: テスト側の簡易DOMヘルパーやスタブの実装不足だけを理由に、実ブラウザや実ランタイムでは必ず存在する標準メソッド（`typeof el.classList?.toggle === "function"` 等）へ不要な存在判定分岐を本番コードに多数追加している箇所。
- 守るべき不変条件: SSR実行時の `typeof window !== "undefined"` 判定や、ブラウザ間で実際に未対応があり得る Web API の機能検出は残す。
- 本番コードに追加された標準DOMメソッド等への不要な存在判定分岐を削除し、必要な要素型を前提とする簡潔な処理へ戻すよう2〜3行で示す。
- テスト側の模擬要素ヘルパーやモック定義に標準メソッド・要素構造を補い、本番と同等の前提で検証が通るように修正するよう示す。
