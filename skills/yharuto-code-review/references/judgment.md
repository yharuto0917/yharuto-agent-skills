# 実コード照合・棄却判定・Code Health 選別基準

候補は仮説であり結論ではない。Stage 3 の収束時および Stage 4 敵対的検証では、本ファイルの基準を適用して誤検知とコード外の些末項目を除外し、実コードの証拠が揃った4区分（`🔴 Bug`・`🟡 Risk`・`🔵 Nit`・`❓ Question`）とコードベースの健全性（Code Health）に基づく判定を確定する。

## 1. Stage 1（`Test Gate`）と Stage 3（本レビュー）の役割境界

- Stage 1 で `NG`（早期差し戻し）にする条件は、変更された実行ロジックに対して実モジュールを呼ぶテストが存在しない場合、今回追加・変更した分岐の異常系や境界値（上限超過・負数・空入力・境界一致など）が欠けている場合、検査対象の関数自体をモック化して戻り値をなぞるだけの場合、または模擬データやモックDOMのフィールド・数量単位・要素階層が実DBスキーマや実コンポーネント定義と食い違っている場合である。ただし `--skip-test` が指定されている場合はテスト判定が `NG` であっても早期差し戻しを行わず、Stage 2〜5 の本レビューを完走する。
- Stage 1 を通過して単体テストが揃っている場合でも、テスト通過だけを根拠に安全と判断してはならない。Stage 3 では単体テスト環境（JSDOMや簡易スタブ）では再現しない実ブラウザの描画領域の切り抜き（モーダルやドロップダウンの `overflow` 切り抜き、ブラウザ固有のビューポート・レイヤー表示APIの対象要素階層ズレにより兄弟の操作部品が描画対象外になる不整合など）、CSSの重なりや背面スクロール固定の解除漏れ、別タブ・ストレージ連携、並行トランザクション競合、差分ビルドのハッシュ更新漏れ、`.toString()` 文字列化埋め込み、およびテストモック不足を補うために本番コードへ追加された過剰な存在判定分岐を深掘りする。

## 2. 実コードとモックの横断照合・4区分分類

指摘を確定させる前に、`workdir` の実ファイルを開いて次の3点を必ず揃える（`🔵 Nit` と `❓ Question` についても実コード上の正確な位置・型や契約・前後のテストや仕様との関係を必ず確認する）。

1. 実コード上の正確な位置（リポジトリ相対パスと行番号）および対象関数・要素・設定の型・契約（または引数と返り値）。
2. 実際に問題が発生する条件、または改善・仕様確認が必要になる具体的な箇所（入力値、画面操作、実行順序、本番とテスト環境の差、仕様書記載との対比）。
3. 呼び出し元・HTML出力・CSS・クライアント処理・DBスキーマ・テストモックを横断して確認した影響範囲。

裏付けが確認できた項目は次の4区分に分類する。

- `🔴 Bug`: 通常操作や想定内の入力で直ちに機能不全・操作不能・データ不整合・認可突破・未処理例外を引き起こす確定不具合（1件以上で必ず `🔴 Request changes`、監査モードでは `🔴 要修正（重大な懸念あり）`）。
- `🟡 Risk`: 通信境界（`origin` 等）や入力の検証漏れ、初期化・並行更新のタイミング競合、空の `catch` 等による例外破棄、差分ビルドのハッシュ計算対象漏れ、および今後の保守で不具合の温床になる構造問題（処理の二重実装、検査不能な文字列化コード、既存共通処理との重複発火、モック都合の過剰防御分岐、型検査回避、共有モジュールへの個別機能分岐の継ぎ足し）。
- `🔵 Nit`: 今回の差分で変更されたコード行に対する非ブロッキングな軽微改善提案（マジックナンバーの定数化、役割が伝わりにくい局所変数名の明確化、冗長な一時変数の整理、簡潔な標準API利用など）。レビュー結論には一切影響しない。
- `❓ Question`: 今回の差分で変更されたコード行に対する非ブロッキングな意図・仕様・境界前提の確認質問（仕様書に記載がない送料重量換算や端数丸め規則の変更、負数・未定義種別の入力をエラーにせずスキップや0扱いする分岐が仕様上の意図通りかなど）。推測で `🔴 Bug` にせず確認質問として出力し、レビュー結論には一切影響しない。

## 3. 棄却4パターン（1つでも該当証拠があれば除外）

疑った経路に対して次のいずれかの証拠を実コードで確認できた場合は、安全と判断して候補から除外する。

1. 上流で検証・遮断済みである場合。対象行単体では不正値や未認可入力で問題が起きそうに見えても、前段のルーター・ミドルウェア・呼び出し元ガードでその入力がすでに除外されており到達しない。
2. 実データがその分岐に入らない場合。理論上は衝突や異常値があり得ても、実際のデータ供給元が一意制約や型制約を持っており該当値が生成されない。
3. 前提が事実誤認だった場合。設定ファイルの有効範囲、Git追跡対象、フレームワークのルーティングやビルド対象を実ファイルで確かめた結果、懸念の前提が成り立たない。
4. 言語・フレームワーク仕様が保証している場合。標準ライブラリ、ORM、ランタイム仕様によってエスケープ・境界安全性・リソース解放がすでに保証されている。

## 4. 修正方針の6点不変条件テスト（`Bug`・`Risk`・`Nit` 共通）

構造改善・簡素化・軽微改善の提案（`guidelines/code-slop.md` の `P0`〜`P5` および5つの関数型変換禁止例外を参照）が次の6点を1つでも破る場合、`🔵 Nit` としても含めずその指摘自体を除外する。

1. 入出力と境界値の一致: `0`・`""`・`false`・`NaN`・`null`・`undefined`・空配列に対する結果が変わらないこと（例として `!(x < 0)` と `x >= 0` は `NaN` で結果が変わる）。
2. 例外伝播と失敗時状態の一致: 外部I/O境界の必要な例外捕捉（I/O 1〜3行を囲み `cause` を添えて再送出する処理等）を削らず、エラー型やステータスコードを変えないこと。
3. 非同期の順序と同時実行数の維持: APIレート制限や順序保証のための直列 `for...of await` を無断で `Promise.all` や `forEach(async)` に変えないこと。
4. フレームワーク制約の遵守: Reactの `useEffect` 等の Hooks 呼び出しより前へ早期 `return` を移動させないこと。
5. リソース解放の維持: `finally`・`using`・`with`・`defer` によるロック・トランザクション・ファイル・タイマーの解放前に素の早期リターンを入れないこと。
6. 計算量と公開仕様の維持: `O(N)` をスプレッド `.reduce()` 等で `O(N^2)` に悪化させず、既存の `export` 名・公開APIのJSONキー名（`legacyWebhookDeliveryId` 等）・DBカラム名の改名を求めないこと。

## 5. コードベースの健全性（Code Health）に基づく判定基準とスコープ境界

- 完璧なコードは存在しない。「指摘が完全ゼロのときだけ `Approve` する」旧基準は採らず、変更全体としてコードベースの健全性（Code Health）が向上している（または高水準を維持している）かを基準に判定する。
- `🟢 Approve`（監査時: `🟢 健全（重大な懸念なし）` も可）: `🔴 Bug` が0件かつ変更起因のCI回帰失敗（`failed`）が0件で、変更全体としてコードベースの健全性が向上している場合。`🔵 Nit` や `❓ Question` は結論に一切影響させず、`Bug` 0件・`Risk` 0件・変更起因CI失敗 0件なら必ず `🟢 Approve` とする。軽微・局所的なフォローアップ向きの `🟡 Risk` が残っていても全体の健全性向上が上回る場合は `🟢 Approve` とし、また `merge_base_sha` 側でも失敗する既存CI失敗（`failed_preexisting`）・`timed_out`・`pending` はサマリー記載にとどめて `🟢 Approve` を妨げない。
- `🟡 Comment`（監査時: `🟡 要確認（構造・保守上の懸念あり）` も可）: `🔴 Bug` と変更起因CI失敗はないが、モック都合の過剰防御分岐の大量追加や共有モジュールの責務混在などの `🟡 Risk` により現状のままではコードベースの健全性が向上しているとは言えず、構造整理や方針確認を求める場合。
- `🔴 Request changes`（監査時: `🔴 要修正（重大な懸念あり）` も可）: `🔴 Bug` が1件以上ある場合、変更起因のCI回帰失敗（`failed`）がある場合、または `.toString()` 二重実装と空 `catch` による例外破棄の複合など深刻な `🟡 Risk` によりコードベースの健全性を明確に悪化させている場合。
- `🔵 Nit` と `❓ Question` は今回の変更対象ファイル（`changed_files`）の変更行に対して出力してよい（第1リンク先は必ず `changed_files` 内のファイルとし、静的文言の軽微な表記や局所変数名を `🔴 Bug` や `🟡 Risk` に過大計上してはならない）。
- 完全除外（`Nit`・`Question` としても一切出力禁止）の対象は、①PR概要・PR本文・PRタイトルの更新漏れや未記入（`TODO` 等）・コミットメッセージ・Issueリンク等のコード外メタ事項、②未変更ファイルに対する軽微指摘・確認質問および `merge_base_sha` 以降の base ブランチ先行コミット、③第3節の棄却4パターン該当候補・第4節の6点不変条件違反、④Linterやフォーマッタが機械検出できる単純な書式差や標準的な外部スタイルシート読込など改善価値のない好みである。
- 同じ原因の `🟡 Risk` や `🔵 Nit` が複数箇所にある場合（モック不足を補う存在判定分岐が複数箇所に追加されている等）は個別見出しに分けず、同一見出し直下の4列表に行を分けて集約する。

## 6. Stage 4 敵対的検証の採否と変更外既存バグの分離

- Stage 4 の応答JSON（`challenged_findings` と `missed_findings`）はそのまま転記せず、メイン側で必ず `workdir` の実コードを開いて再照合する。
- 反証側に実コード上の裏付け（棄却4パターン該当、6点不変条件違反、PR概要等のコード外メタ指摘、未変更ファイルへの `Nit`・`Question`、Linter検出済みの単純体裁）があれば候補を削除し、軽微事項が `Risk` に過大計上されていれば `Nit` へ修正する。反証側が実コードを読み違えている場合は事実に基づいて候補を残す。
- 新規見落とし候補（`missed_findings` の `Bug`・`Risk`・`Nit`・`Question`）は、実コードで行番号・条件・影響範囲が確認できたものだけを採用する。変更コード上の仕様書未記載の挙動変更（丸め規則の変更や負数入力のスキップ分岐など）は、`## 指摘事項` 内の `### ❓ Question:` として変更ファイルを第1リンクに指定して出力する。
- 周辺調査中に未変更の既存ファイル内でゼロ除算や認証欠落などの明白な重大既存バグを発見した場合は、変更コードの指摘（`Bug`・`Risk`・`Nit`・`Question`）には混ぜず、`## CI・敵対的検証サマリー` 末尾に最大2件まで「変更外ファイルの既存懸念」として分離付記する。
