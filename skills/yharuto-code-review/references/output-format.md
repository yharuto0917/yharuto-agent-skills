# レビュー出力構造・強調判定・日本語校正規則

読み手はこれから初めてコード本体を見る前提で構造化する。仕様と箇所は表へ、波及経路は `mermaid` 図へ、問題・提案・確認事項は役割の日本語による短い箇条書きへ分離し、文体は丁寧語（`です・ます`）に統一する。

## 1. 絵文字の厳格制限と見出し正規表現

絵文字の使用は次の2つの見出し正規表現に完全一致する行のみに限定し、Alert本文・箇条書き・表・サマリー・見出し要約文中には一切置かない（`❓ Question:` の要約文末尾等にも絵文字 `❓` は置かず、「〜は仕様上の意図通りか」「〜へ変更した意図の確認」または全角 `？` を用いる）。

- 判定見出し（H2）: `^## レビュー判定: (🛑 Test Gate NG（テスト修正差し戻し）|🔴 Request changes|🟡 Comment|🟢 Approve|🔴 要修正（重大な懸念あり）|🟡 要確認（構造・保守上の懸念あり）|🟢 健全（重大な懸念なし）)$`
- 項目見出し（H3）: `^### (🔴 Bug|🟡 Risk|🔵 Nit|❓ Question|🛑 Test Issue): [^\U0001F000-\U0001FAFF\u2600-\u27BF]+$`

## 2. モード①: Stage 1 `NG` 早期差し戻し形式（`stage1_ng`）

Stage 1 でテスト欠落やモック乖離が見つかった場合（`--skip-test` 未指定時）は、本レビュー指摘を出さず次の3セクションで構成する。なお `--skip-test` 指定時は Stage 1 が `NG` または `SKIP` でも早期差し戻しを行わず、必ずモード②（`full`）またはモード③（`audit`）で Stage 2〜5 を完走し、Stage 1 の評価結果（例: `NG（--skip-test 指定により継続）`）を `## CI・敵対的検証サマリー` に明記する。`### 🛑 Test Issue:` 直下では変更コード行と不備のあるテスト行を4列表で対比し、「現在のテストやモックのどこが実仕様と乖離してどの不具合を見逃すか」と「2〜3行の修正方針」を示す。

## 3. モード②: 通常完走形式（`full`）と Code Health 判定Alert 3種

セクション順は `## 変更概要` → `## レビュー判定: ...` → `## 指摘事項` → `## CI・敵対的検証サマリー` で固定する。

1. `🔴 Bug` が1件以上、変更起因のCI回帰失敗（`failed`）あり、または深刻な `🟡 Risk` で健全性を明確に悪化させているとき: `## レビュー判定: 🔴 Request changes` と `> [!CAUTION]`。
2. `🔴 Bug` と変更起因CI失敗はないが、モック都合の過剰防御分岐や共有モジュールの責務混在などの `🟡 Risk` により現状では健全性向上が認められず確認を求めるとき: `## レビュー判定: 🟡 Comment` と `> [!WARNING]`。
3. `🔴 Bug` と変更起因のCI回帰失敗（`failed`）が0件で、変更全体としてコードベースの健全性（Code Health）が向上しているとき: `## レビュー判定: 🟢 Approve` と `> [!TIP]`（`🔵 Nit`・`❓ Question`・軽微な `🟡 Risk`、および base既存の `failed_preexisting`・`timed_out`・`pending` は `🟢 Approve` を妨げない。4区分すべて0件のときのみ `## 指摘事項` 本文を「`対応が必要な不具合（Bug）・懸念（Risk）および変更コードへの軽微な提案（Nit）・確認質問（Question）は検出されませんでした。`」の1文のみとする）。

## 4. モード③: 全体・指定パス監査形式（`audit`）

`--audit` モードでは第1見出しに `## 監査概要`（`## 変更概要` も許容）、3列表に `| ファイル | 種別 | 役割と主な内容 |`（従来ヘッダも許容）、範囲箇条書きに `- 監査対象範囲:` / `- 監査対象外範囲:`（従来表記も許容）＋ `mermaid` 図を用いる。第2見出しは監査向け判定（`🔴 要修正（重大な懸念あり）` → `[!CAUTION]`、`🟡 要確認（構造・保守上の懸念あり）` → `[!WARNING]`、`🟢 健全（重大な懸念なし）` → `[!TIP]`）または従来の3種を選択し、以降はモード②と同じ構造とする。

## 5. 表ヘッダ・簡潔記法・リンク・コード制限・日本語校正の厳守事項

1. 4列表の第3列ヘッダは `| 箇所 | 対象 | 型・契約 | 処理内容と目的 |` を標準とし、後方互換として `| 箇所 | 対象 | 引数と返り値 | 処理内容と目的 |` も許容する。1行1対象・1セル最大1リンクとし、リンクは `[ModalSheet.tsx:L24-L38](src/ModalSheet.tsx#L24-L38)` のようにリポジトリ相対パスで書く（`yharuto-review-`・`/.gemini/tmp/`・`/var/folders/`・`/tmp/`・`file:///` は禁止、セル内の型 `|` は `\|` にエスケープ）。
2. `### 🔴 Bug:`・`### 🟡 Risk:`・`### 🛑 Test Issue:` は「4列表＋箇条書き2項目以上」を必須とする。非ブロッキングな `### 🔵 Nit:` と `### ❓ Question:` は、①「4列表＋箇条書き（1項目以上）」または ②「表なしの簡潔箇条書き（1〜3項目、最初の箇条書き内にリポジトリ相対リンクを最低1つ含む）」のいずれかで記述し、第1リンク先は必ず `changed_files` 内のファイルとする（PR概要更新漏れ等のコード外メタ事項は禁止）。
3. 具体的な関数名・変数名・セレクタ名は表（または簡潔記法のリンク箇所）にとどめ、地の文では「モーダル枠」「出力ジョブ」「初期化スクリプト」のように役割の日本語で書く。`mermaid` 以外の4行以上のコードブロックを一切出力せず、ノードラベルに記号を含む場合は `A["引当上限を照合"]` のように二重引用符で囲む。
4. 日本語校正7原則を守る。①確定事項は言い切り未確認事項と混ぜない。②比喩動詞（`壊れる`・`静かに壊れる`・`黙って失敗する`・`潰す`・`握りつぶす`）を避けて実際の現象を書く。③不自然な擬人化や直訳語（`事情を知りすぎている`・`偽緑`・`根因`）を使わない。④硬い冗長表現（`多角的な観点から`・`整合性を担保する`・`検証を実施する`・`〜することが可能です`・`ファンクション`）や地の文の素の `ゲート` を避け、補助動詞・形式名詞（`してください`・`できます`・`すること`・`するため`）をひらがなにする。⑤短い主語直後の不要な読点（`この関数は、`・`Aではなく、B`）を打たない。⑥前置きフィラー（`重要なのは`・`結論から言うと`・`特筆すべきは`）を削る。⑦許可見出し以外の絵文字・装飾ダッシュ・文末コロンを使わない。
