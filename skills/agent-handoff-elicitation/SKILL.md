# Agent Handoff Elicitation

このスキルは、前任Agentから作業を受け継ぐときに、受け手Agentがすぐ再開できるだけの情報を引き出すためのものだ。目的は「会話の要約」ではなく、「次のAgentが同じ調査をやり直さず、誤った前提を引き継がず、残タスクを安全に進められる状態」を作ることにある。

前任Agentに隠れた思考過程の逐語開示を求めない。代わりに、判断理由、証拠、棄却した仮説、不確実性、作業上の勘所を簡潔な要約として出させる。引き継ぎで必要なのは内面の全文ではなく、再利用できる意思決定の痕跡だからだ。

## 基本方針

引き継ぎを受けるときは、まず「前任Agentに何を吐かせるべきか」を明示する。曖昧な「これまでのまとめをください」では足りない。前任Agentには、完了条件、現在地、未完了、検証済み/未検証、危険な前提、触ったファイル、実行したコマンド、次にやるべきことを構造化して出させる。

引き継ぎ文は、以下の3つを同時に満たす必要がある。

- **再開可能性**: 次のAgentが最初の30分を探索で浪費せず、具体的な次アクションに入れる。
- **検証可能性**: 「できた」「直した」などの主張に、ファイル、コマンド、出力、テスト結果、未実行理由が紐づいている。
- **誤継承の防止**: 不確実なこと、推測、失敗した試行、触ってはいけない変更、ユーザーの意図を明示している。

## 使う場面

このスキルを使う典型例:

- ユーザーが「別Agentから引き継いで」「前のスレッドの続き」「この作業をhandoffしたい」と言う。
- コンテキスト圧縮、スレッド移動、担当交代の前に、前任Agentへ引き継ぎ依頼を書く。
- 前任Agentの要約が薄く、受け手として不足情報を追加で質問する必要がある。
- 長い実装、調査、レビュー、デバッグ、ドキュメント作成の途中状態を次のAgentへ渡す。
- 自分が前任Agentとして、次のAgentに渡すハンドオフを作る。

## 最初に判断すること

1. **前任Agentと直接やり取りできるか。**
   できるなら、下の「前任Agentへの依頼文」を送る。できないなら、リポジトリ、会話履歴、作業ログ、差分、テスト結果から「再構成ハンドオフ」を作る。
2. **受け手が今すぐ続行するのか、ユーザーに判断してもらうのか。**
   続行するなら、ハンドオフを読んだ後に不足情報だけを確認し、作業を進める。判断待ちなら、ハンドオフと残課題を短く提示する。
3. **高リスク領域があるか。**
   セキュリティ、金銭、データ破壊、認証、外部送信、破壊的コマンドが絡む場合は、検証済み/未検証と権限境界を特に厚く出させる。

## 前任Agentへの依頼文

前任Agentにそのまま送る。必要ならプロジェクト名や現在の依頼文だけ差し替える。

```text
あなたはこの作業を次のAgentへ引き継ぐ前任Agentです。
隠れた思考過程の逐語開示や秘密値は出さないでください。代わりに、次のAgentが安全に再開するための判断理由・証拠・未確定事項を構造化して出してください。

以下のテンプレートを埋めてください。分からない項目は「不明」と書き、推測は推測だと明記してください。「完了」「確認済み」と書く場合は、根拠となるファイル、コマンド、出力、テスト結果、または会話上の根拠を添えてください。

# Handoff Brief

## 1. 目的と完了条件
- ユーザーの最終目的:
- 今回の作業で満たすべき完了条件:
- 完了条件のうち、完了済み:
- 未完了または曖昧な条件:

## 2. 現在地
- 現在の作業状態:
- 最後に行った具体的な作業:
- 次に着手すべき最小ステップ:
- 途中で止まった理由:

## 3. ユーザー指示・好み・制約
- 明示されたユーザー指示:
- 暗黙に尊重すべき好み:
- 触ってはいけないもの、避けるべき操作:
- 期限、品質基準、出力形式:

## 4. 環境・権限・外部状態
- 作業ディレクトリ、ブランチ、主要ファイル:
- 利用したツール、サーバ、セッション:
- 必要な環境変数や秘密情報の有無（値は書かない）:
- ネットワーク、権限、サンドボックス上の制約:

## 5. 変更・成果物
- 変更したファイルと要点:
- 作成した成果物と場所:
- 未保存、未コミット、未反映の変更:
- ユーザーまたは他者が触った可能性のある変更:

## 6. 実行したコマンド・検証
- 実行した重要コマンド:
- 成功した検証と結果:
- 失敗した検証、エラー、再実行時の注意:
- まだ実行していない検証と、その理由:

## 7. 判断理由と設計メモ
- 主要な判断と、その理由:
- 採用しなかった案と、棄却理由:
- 守るべき不変条件、前提、ドメイン知識:
- 次のAgentが誤解しやすい点:

## 8. 調査ログと発見
- 読んだファイル、ドキュメント、Issue、PR:
- 重要な発見:
- 追う価値が低いと分かった探索:
- まだ裏取りが必要な仮説:

## 9. リスク・不確実性・ブロッカー
- 既知のリスク:
- 不確実な前提:
- ブロッカー:
- ユーザー確認が必要な事項:

## 10. 次のAgentへの実行プラン
- 優先順位つきの次アクション:
- 最初に確認すべきファイル/コマンド:
- 失敗した場合の代替案:
- 完了時にユーザーへ報告すべきこと:

## 11. 短い再開チェックリスト
- [ ] 作業ツリー/ファイル状態を確認する
- [ ] 未完了条件を確認する
- [ ] 最新の検証結果を確認する
- [ ] 次の最小ステップを実行する
- [ ] 変更後に必要な検証を実行する
```

## 不足しているときの追質問

前任Agentの返答が薄い場合は、礼儀正しく追加で絞る。質問は一度に多くしすぎず、再開を妨げる不足に集中する。

使いやすい追質問:

- 「変更したファイルを絶対パスまたはリポジトリ相対パスで列挙し、各ファイルで何を変えたか1行ずつ書いてください。」
- 「『完了』と判断した根拠のコマンド、テスト結果、または確認方法を具体的に書いてください。未実行なら未実行と書いてください。」
- 「採用しなかった案、失敗した試行、もう追わなくてよい探索を教えてください。次のAgentが同じ時間を使わないためです。」
- 「不確実な前提を、確信度つきで列挙してください。高リスクな推測を先頭にしてください。」
- 「次のAgentが最初に開くべきファイルと、最初に実行すべき安全なコマンドを3つ以内で指定してください。」

## 受け取ったハンドオフの品質チェック

ハンドオフを受け取ったら、次の質問に答えられるか確認する。答えられない項目があるなら、前任Agentへ追質問するか、自分で再構成する。

- 何を達成しようとしているのか。
- 完了条件は何で、どこまで満たしたのか。
- 具体的にどのファイル、データ、外部状態が変わったのか。
- 何を検証し、何を検証していないのか。
- どの判断が推測で、どの判断が証拠つきなのか。
- 同じ罠にはまらないために、失敗した探索や棄却済み案が書かれているか。
- ユーザーの強い希望、禁止事項、最新の指示が残っているか。
- 次にやるべき最小ステップが、ファイル名やコマンドレベルで書かれているか。

## 前任Agentがいない場合の再構成手順

直接聞けない場合は、受け手Agentが自分でハンドオフを再構成する。

1. 会話の最新依頼、システム制約、ユーザーの追加指示を読み直す。
2. 作業ディレクトリ、ファイル一覧、変更状態、生成物を確認する。
3. 差分、最近触られたファイル、テストやログの痕跡を見て現在地を推定する。
4. 安全に実行できる軽い検証だけを行い、破壊的操作や外部送信は避ける。
5. 「確認済み」と「推測」を分けて、再構成ハンドオフを書く。
6. 不確実性が作業継続のリスクになる場合だけ、ユーザーに短く確認する。

再構成ハンドオフでは、自信のない部分を曖昧に塗りつぶさない。受け手にとって有害なのは「分からないこと」よりも、「分かっていないことが分からない状態」だからだ。

## 思考方法として引き出すべき情報

前任Agentから引き出したいのは、内部独白ではなく、次のAgentが再利用できる判断モデルである。特に以下を要求する。

- **目的モデル**: 何を最適化していたか。速度、品質、互換性、ユーザーの好み、リスク低減のどれを優先したか。
- **境界モデル**: どこまでが今回の責務で、どこからが別タスクか。
- **不変条件**: 壊してはいけない契約、既存挙動、データ形式、UI/UX、API、権限境界。
- **仮説と反証**: 何を疑い、どう確かめ、何を棄却したか。
- **探索戦略**: どのファイルやログから読んだか。なぜそこを優先したか。
- **リスク評価**: 何が一番壊れやすいか。発生確率と損害の見積もり。
- **検証戦略**: 何を動かせば完了を確認できるか。実行できない場合は代替確認があるか。

これらは短くてよいが、必ず「なぜそう判断したか」を一段だけ添える。次のAgentはその理由を使って、状況が変わったときに判断を更新できる。

## 出してはいけないもの

- 秘密値、トークン、パスワード、個人情報の不要な転載。
- 隠れた思考過程や内部独白の逐語開示。
- 長い生ログの丸ごと貼り付け。必要箇所を要約し、ファイルやコマンドで参照できるようにする。
- 「多分大丈夫」「だいたい完了」だけの根拠なし完了宣言。
- ユーザーが明示していない破壊的操作の提案。
- 他者の未確認変更を自分の成果として扱うこと。

## 受け手Agentの最初の応答

ユーザーが「引き継いで」と言ったとき、前任Agentからの情報がまだないなら、まずハンドオフ依頼文を出すか、前任Agentに送ることを提案する。すでにハンドオフがあるなら、読み取った現在地、不足情報、次にやることを短く伝えてから作業に入る。

例:

```text
引き継ぎとして見るべき情報は、目的、現在地、変更済みファイル、検証結果、未完了、判断理由、次の最小ステップです。前任Agentに以下のテンプレートで出してもらえば、こちらで重複調査を減らして再開できます。
```

## 良いハンドオフの目安

良いハンドオフは、長さより密度で判断する。短くても、受け手が次のコマンドを迷わず選べるなら良い。長くても、主張の根拠と未完了が分からないなら悪い。

特に価値が高い情報:

- 「このコマンドは失敗した。原因はここまで分かっている。」
- 「この案は試したが、ユーザー要件に合わないので棄却した。」
- 「このファイルは触っていない。似た名前の別ファイルを触った。」
- 「テストは通ったが、E2Eは未実行。理由はローカル依存サービスがないため。」
- 「次はこの1ファイルを直せばよい。広いリファクタは不要。」

価値が低い情報:

- 「いろいろ調査しました。」
- 「ほぼ完成です。」
- 「詳細はコードを見てください。」
- 「問題なさそうです。」
- 「次のAgentなら分かると思います。」
