# コードレビューの判断の型

このスキルは暗記用チェックリストではなく、判断の型を与えるものだ。なぜなら、チェックリストは既知の欠陥しか捕まえられないが、実際のレビュー価値は「未知のコードのここが変だ」という嗅覚と、その疑いを証拠で確定/棄却する推論から生まれるからだ。以下は特定の言語・プロジェクトに依存しない判断基準として書く。具体例は「例：」で添えるが、基準そのものは一般化して読むこと。

原則として、すべての判断は「〜という状況では〜する。なぜなら〜だからだ」で組み立てる。確信の持てる判断は短く、迷いやすい判断（特に棄却）は厚く扱う。

## 1. 読み始める前 — オリエンテーション

**未知のコードベースや大きな差分を渡された状況では、いきなり個別ファイルを開かず先に「地図」を作る。なぜなら、部分の良し悪しは全体の責務配置を知らないと判断できないからだ。** 例：会計ロジックがUIコンポーネント内にあること自体が欠陥だと気づくには、「それが本来どの層にあるべきか」という地図が先に要る。

地図作りの手段は、得たい情報で選ぶ：

- **規模と異常を掴みたい状況では、ファイル一覧と行数分布をまず取る。なぜなら、全体量と「不釣り合いに大きいファイル」（責務過多の候補）が一目で分かり、精読の優先度がつくからだ。** ただしサイズは注意喚起であって優先度そのものではない（→ 2節）。
- **コードベースの健全性を推し量りたい状況では、ディレクトリ命名と構成の乱れを見る。なぜなら、命名の綴り誤りや規約違反が定着している場合、「レビューの目が入っていないコード」というシグナルで、他の箇所にも粗が多いと予測できるからだ。**
- **検証の当たりをつけたい状況では、言語・フレームワークを特定し、それ固有の危険地帯を想起する。なぜなら、探すべき壊れ方の類型がスタックで変わるからだ。** 例：サーバ/クライアント境界を持つWebフレームワークなら境界を越えるデータ、トランザクションを持つDBなら並行更新と権限ルール。

読み方の方針を左右する変数と、その分岐：

- **レビューの種類。** 全体監査を求められた状況では網羅性を主軸に領域分割して機械的に全ファイルをカバーする。単一PRなら差分とその波及に集中する。なぜなら、目的が違えば読むべき範囲が違い、「見落としがない」は網羅でしか担保できないからだ。
- **変更の性質。** 新機能なら設計と境界を、バグ修正なら「本当に直ったか＋副作用」を、リファクタなら「外部から見た振る舞いが不変か」を主軸にする。なぜなら、それぞれで最も壊れやすい面が違うからだ。
- **リスクの所在。** 金銭・認証・データ書き込みに触れる箇所を最優先に置く。なぜなら、そこの欠陥は他カテゴリより損害が桁違いだからだ。

分岐点の例：「全ファイルを順に読む」か「リスクの高い領域から読む」か → 通常は後者を選ぶ。なぜなら、レビューの価値はcritical発見に偏り、時間は有限だからだ。**ただし網羅監査を明示的に求められた状況では前者に寄せ、機械的にでも全ファイルを走査する。** 損害の非対称性が「見落としの害 > 冗長に読む害」に傾くからだ。

## 2. パターン認識 — どこを精読し、どこを流すか

この嗅覚の土台は、「同じ欠陥は環境が変わっても再発する」という帰納だ。並行性・信頼境界・状態の一意性・エラー伝播・リソース解放といった、言語を超えて共通する"壊れ方の類型"を知っていることが、精読シグナルの正体である。

### 精読すべきシグナル（「ここは危ない」）

- **一意性・順序・件数を自前で計算している状況では精読する。なぜなら、分散・並行環境で一意性を自前計算するとほぼ競合するからだ。** 例：件数+1でIDや連番を採番する。
- **副作用を伴う非同期処理が、正しく待たれているか怪しい形の状況では精読する。なぜなら、待ち漏れは完了順序とエラー伝播が静かに壊れる定番だからだ。** 例：配列の反復に非同期コールバックを渡し、その完了を待たずに後続処理へ進む。
- **読んで加工して書き戻す（read-modify-write）がトランザクション外の状況では精読する。なぜなら、並行更新でロスト更新が起きる典型だからだ。**
- **サーバの入口に認証・認可チェックが「見当たらない」状況では、あえて時間をかけて確認する。なぜなら、セキュリティは"ある機能"ではなく"ない防御"で破れ、欠落は差分に現れず静かだからだ。** だから「あるべき防御がない」を能動的に探す。
- **外部入力が特権操作へ流れる状況では精読する。なぜなら、入力を信頼した瞬間に権限昇格や乗っ取りが生まれるからだ。** 例：呼び出し側が渡した識別子を検証せず管理操作に渡す。
- **金額・数量・日付の計算がある状況では精読する。なぜなら、金銭や在庫は誤差が実損に直結し、かつテストが薄い領域だからだ。**
- **秘密・設定（鍵、認証情報、エンドポイントURL）が絡む状況では精読する。なぜなら、一度漏れると回収不能で影響が長期に及ぶからだ。**
- **対になった名前や連番のコンポーネントを見た状況では精読する。なぜなら、コピペ由来なら片方のバグは他方にもあり、片方だけ修正されて不整合が残るからだ。** 例：ほぼ同型の2系統のうち片方だけが、コピペ時に識別子の意味がずれて機能不全になっていた。

### 流して良い条件

- **生成物・テンプレート由来で未改変のコードは流してよい。なぜなら、上流でレビュー済みで、改変がなければ新規リスクは入らないからだ。ただし「改変されていないこと」を差分で確認してから流す。** 改変があれば精読対象に戻す。
- **純粋な表示・整形で、副作用も外部入力も金銭も絡まないコードは流してよい。なぜなら、壊れても損害が表示崩れに留まり、リスク階層が低いからだ。**

分岐点の明示：「大きいファイル＝精読」とすべきか？ → **行数だけでは決めない。なぜなら、大きくても定型的な宣言の羅列ならリスクは低く、小さくても認可の入口なら最重要だからだ。** サイズは「見ておけ」の合図であって、優先度そのものではない。

## 3. 疑い → 検証 → 判定

基本姿勢：**疑いは仮説であって結論ではない。「まずい気がする」で止めず、その主張が成り立つ条件と、それを覆す反証の両方を探す。なぜなら、レビュアーの誤検知はコストが高い（信頼を失い、無駄な修正を生む）からだ。**

### 検証手段の選択基準（何で確かめるか）

- **「この関数はこう呼ばれる/呼ばれない」が争点の状況では、呼び出し元をたどるか全参照をgrepで数える。なぜなら、実際の使われ方が主張の成否を決めるからだ。**
- **「ここに防御・処理がない」が主張の状況では、対象範囲（ファイル全体と関連層）を通読し、該当キーワードの不在を全走査で確定する。なぜなら、「ない」の証明は部分読みでは不可能で、範囲を区切った全走査でしか言えないからだ。** 例：認可欠如は、入口ファイル全体に認証参照がゼロだと確認して初めて確定できた。
- **「実データがこうなる」が主張の状況では、リポジトリ内の実データ・テストデータ・型定義を突き合わせる。なぜなら、抽象的な懸念より一つの実例が雄弁だからだ。**
- **主張がgitの状態を前提にする状況では、追跡・無視の状態をコマンドで確認する。なぜなら、「コミットされている」と「ローカルにあるだけ」は結論が正反対で、思い込みで断定すると誤りになるからだ。**
- **「実行時に壊れる」が争点の状況では、可能なら動かして観察する。ただし読み取り専用や破壊的操作の懸念がある状況では、コード追跡と型確認で代替する。なぜなら、検証の確実性と副作用リスクを常に天秤にかけるからだ。**

### 判定境界（問題あり / なし）

- **「問題あり」と確定してよいのは、発火する具体的条件（入力・状態・タイミング）を一つ以上言えるときだけだ。なぜなら、再現条件を言えない指摘は反証不能で、読み手が行動できないからだ。**
- **「問題なし」と棄却してよいのは、疑った失敗経路が実際には塞がれている証拠を見つけたときだ**（次項）。

### 棄却の思考過程（最重要）

「疑ったが問題なし」と判断してよいのは、次のいずれかの証拠が得られたときだ。ここに再利用価値の高いパターンが集中している。

1. **上流にガードが既に存在する。** 「nullや不正値で落ちる」と疑った状況では、危険な操作に到達する前段でその値が除外されていれば棄却する。なぜなら、危険な行に至る道が塞がれていれば経路は発火しないからだ。だから「危ない行」だけでなく「そこに至る道」を必ず見る。
2. **実際に流れるデータがその分岐に入らない。** 「重複・衝突で壊れる」と疑った状況では、実フローで問題の値が生成されない（単一ソースから一意に供給される等）と確認できたら棄却する。なぜなら、理論上あり得る入力ではなく、実際に流れる入力が結果を決めるからだ。
3. **主張の前提が事実誤認だった。** 「秘密が露出している」「この設定が効いている」と疑った状況では、前提をコマンドや一次情報で裏取りし、崩れたら棄却または格下げする。なぜなら、前提が崩れれば結論も崩れるからだ。**特に、自分や他者の"それらしい指摘"ほど前提を機械的に裏取りする。もっともらしさは正しさではない。** 例：重大と付いた指摘の前提が、簡単なコマンド一つで否定できることがある。
4. **仕様・言語がその挙動を保証している。** あるAPIや構文が「失敗しそう」と疑った状況では、仕様上有効だと確認できたら棄却する。なぜなら、自分の不慣れを欠陥と誤認していることがあるからだ。ただし仕様を確認しきれない場合は棄却せず「不確実」に落とす（→ 6節）。

棄却で犯しやすい誤りと対処：

- **証拠なく「たぶん大丈夫」で流してはならない。なぜなら、棄却も確定と同じく証拠を要するからだ。** 証拠が出せないなら、棄却ではなく「不確実」として残す。
- **迷ったときの倒し方の分岐：** 自分の指摘を潰しにいく敵対的検証では、**確証が持てなければ棄却に倒す。なぜなら、誤検知（狼少年）はレビュー全体の信頼を毀損し、真の指摘まで無視されるからだ。ただし、人命・金銭・データ破壊に関わる重大な安全性の疑いはこの限りでなく、確証がなくても「未確定の重大懸念」として残す。** そこだけ損害の非対称性（見逃しの害 > 誤報の害）が逆転するからだ。

分岐点の明示：「棄却」か「不確実として残す」か → **反証の証拠があるなら棄却、証拠も確証も出せないなら不確実。** 両者を混同しないのは、読み手が後で「調査済みで安全」なのか「未調査」なのかを区別できるようにするためだ。

## 4. 見落としを防ぐチェック観点（トリガー / 確認 / OK基準）

網羅暗記ではなく、トリガーが引かれたカテゴリだけを起動する。各カテゴリは「何が起動条件か・何を見るか・どうなればOKか」で持つ。

- **正確性（ロジック）。** トリガー＝計算・条件分岐・境界値・状態遷移がある。確認＝オフバイワン、境界（0・空・最大）、取りこぼす状態。OK＝想定入力の全クラスで正しい出力を経路として説明できる。
- **セキュリティ。** トリガー＝認証・認可・入力・秘密・信頼境界に触れる。確認＝入口の認証、特権操作の認可、外部入力の検証、秘密の露出、権限昇格経路。OK＝「あるべき防御」を先に列挙し、各々の存在を確認できた。なぜ列挙から入るか：セキュリティは欠落で破れるので、「あるもの」を眺めるより「ないもの」を探す方が効くからだ。
- **並行性・データ整合。** トリガー＝共有状態への書き込み、採番、残高・在庫の更新、複数ステップ更新。確認＝トランザクション有無、read-modify-write、冪等性、そして**取り消し・削除時の巻き戻し（補償処理）の有無**。OK＝「同時実行・再実行・途中失敗」の3シナリオで台帳が破綻しない。**減算があるなら対になる復元があるかを必ず対で見る。なぜなら、台帳は増減の対称性が崩れた瞬間に信頼を失うからだ。**
- **エラーハンドリング。** トリガー＝非同期の待ち、外部呼び出し、I/O。確認＝例外の握りつぶし、待ち漏れ、失敗時のユーザー通知と状態復帰。OK＝失敗経路が成功経路と同じくらい明示的に扱われている。
- **パフォーマンス。** トリガー＝ループ内クエリ、全件取得、描画内フェッチ。確認＝N+1、不要な全件取得、再レンダー誘発。OK＝データ量が増えても計算量が破綻せず、必要な分だけ取っている。ただし実測の裏付けのない早すぎる最適化は指摘しない（→ 5節）。
- **設計・保守性。** トリガー＝重複、責務の混在、境界の漏れ。確認＝コピペ対、UIとデータ取得の混在、単一情報源の不在。OK＝変更が一箇所で完結し、責務が層に分かれている。
- **命名・ハイジーン。** トリガー＝常時（ただし低優先）。確認＝タイポ、規約違反、デッドコード、追跡すべきでないファイル。OK＝意図が名前で読める。永続層に固着したタイポは扱いを5節で判断する。

## 5. 指摘の重み付けと取捨選択

**severityは「損害の大きさ × 発生確率」で決める。なぜなら、レビューの目的は読み手の行動を"最も損害の減る順"に導くことだからだ。**

- critical：セキュリティ侵害、データ・金銭の損失、認証バイパス。最上位に置く理由は、回復不能または金銭直結だからだ。
- high：ユーザーに現れる明確なバグ、重大な設計欠陥。
- medium：限定条件で出るバグ、保守性・性能。
- low：スタイル・命名。

指摘する / しないの線引き：

- **指摘する状況：** 発火条件が言え、読み手が直せる粒度である。
- **指摘しない・格下げする状況とその理由：**
  - (a) **実測の裏付けがない性能改善は指摘しない。なぜなら、憶測の性能指摘は工数を奪い、効果が不明だからだ。**
  - (b) **修正コストが損害を上回る固着問題（永続層に定着したタイポ等）は格下げする。なぜなら、レビューは正しさの追求ではなく損害最小化だからだ。ただし「なぜ今直さないか」を添えて記録は残す。**
  - (c) **チーム規約に反しない純粋な好みは指摘しない。なぜなら、レビュアーの好みの押し付けは信頼を減らすからだ。**

文脈変数による重みの調整：**同じ指摘でも、「短命・高並行・訂正不能な取引」を扱うドメインでは並行性バグの重みが上がる。なぜなら、その文脈では発生確率と訂正不能性が跳ね上がるからだ。** 文脈が不明なら、ドメインから推測して重みを調整し、その推測を明示する。

## 6. 自分の判断の不確実性の扱い

- **確証が持てない指摘は、消さずに「不確実」と明示して残す。なぜなら、レビュアーの役割は白黒つけることだけでなく、読み手が調べるべき場所を示すことでもあるからだ。** 断定と示唆は文体で書き分ける。
- **知識不足の領域に遭遇した状況では、憶測で断定しない。まず一次情報（仕様・型・実装）に当たり、当たれないなら「要確認」と明記して読み手に委ねる。なぜなら、自信ありげな誤りは沈黙より有害だからだ。**
- **検証を途中で打ち切らざるを得ない状況（時間・上限）では、「検証済み」と「未検証」を必ず分けて報告する。なぜなら、両者を混ぜると読み手が確度を測れず、全体の信頼が落ちるからだ。**
- **他者（自動ツール・別のレビュアー・過去の自分）の指摘を扱う状況では、もっともらしさで採用せず、前提を裏取りしてから通す。なぜなら、上流の誤りをそのまま増幅すると、レビュー全体が誤情報の運び屋になるからだ。**

**メタ原則：レビューの品質は「見つけた数」ではなく「確度 × 損害順の並び」で決まる。なぜなら、読み手の時間も有限で、確度の低い大量の指摘は真の重大問題を埋もれさせるからだ。** 迷ったら、指摘を増やす方向ではなく、確度と並び順を上げる方向に労力を割く。
